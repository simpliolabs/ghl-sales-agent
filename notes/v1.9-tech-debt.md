# v1.9 Tech Debt — Lint Grandfather Exceptions

Created: 2026-05-27
Status: TRACKED, not blocking v1.9 ship

## Background

v1.9 introduced two ESLint custom rules:
- `adorb-v19/no-direct-leads-write` — forbids direct `db.update(leads).set()` outside canonical handlers
- `adorb-v19/no-direct-outbox-status-write` — forbids raw `UPDATE outbox SET outbox_status` SQL outside canonical files

Rules added in PR #8 (Phase 1.C+1.D addendum).

## Grandfather Exceptions

The following files have pre-v1.9 violations that were grandfathered to avoid scope creep in PR #8:

| File | Violations | Lines | Rationale |
|---|---|---|---|
| `server/brain-adapter.ts` | 2 | 216, 438 | Pre-v1.9 brain output → lead state writes |
| `server/scheduling-engine.ts` | 4 | 991, 1009, 1026, 1168 | Pre-v1.9 scheduling logic writes |
| `server/webhook-events.ts` | 5 | 193, 262, 271, 280, 288 | Pre-v1.9 webhook event handlers |

**Total pre-existing violations:** 11 (per Manus PR #8 addendum audit, 2026-05-27)

### `no-direct-outbox-status-write` exceptions

None beyond the already-allowed files (`outbox-worker.ts`, `compose-and-send.ts`, `apply-compose-outcome.ts`, `crons.ts`).

## Migration Plan (Phase 2)

Each callsite migrates to `updateLeadFields()` or `setLeadState()` (per spec §6).

**Order of migration (by risk, lowest first):**
1. `server/scheduling-engine.ts` — scheduling-only writes, low coupling
2. `server/webhook-events.ts` — event handler writes, moderate coupling
3. `server/brain-adapter.ts` — brain output writes, highest coupling

**Acceptance per file:**
- All direct `db.update(leads)` removed
- Remove file from grandfather list in `eslint.config.mjs`
- `npm run lint` clean after removal
- Existing tests still pass

## Why This Was Deferred

Karpathy Principle 3 (Surgical Changes): PR #8 scope is Phase 1.C+1.D callsite migration and crons. Migrating 11 pre-existing violations across 3 unrelated files would be drive-by refactor. Each migration carries regression risk that needs its own review cycle.

## When To Tackle

After v1.9 is live, verified clean for 7+ days, and the 13 failure-mode catalog cases are observed in production. Once we have real traffic flowing through the v1.9 pipeline, we can confidently migrate the grandfather files.

Estimated effort: 2-4 hours per file (read, migrate, test, verify).
